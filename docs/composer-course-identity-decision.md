# T4 course identity decision refinement

Original read-only investigation, 2026-11-16, before T4 implementation. Current candidate implementation uses the [staged migration recipe](composer-course-migration.md); consult the [compatibility ledger](composer-compatibility.md) for actual installed acceptance. This refines the alternatives in [T4 issue #54](https://github.com/zudolab/pinsel/issues/54) and the [migration plan](composer-migration-plan.md). The generic Mapping source is implemented in the current candidate package; this decision document alone is not evidence of completed migration or browser acceptance. All existing Content fields and values remain retained as recorded in the [field inventory](composer-migration-inventory.md) and [reference map](composer-migration-reference-map.json).

## Finding: a duplicate immutable key is not supported by current native Content policy

`src/content/model/types.ts` defines ContentFieldDefinition as id/key/label/required + ContentValueSchema. There is no immutable/read-only field flag. `src/content/model/validate.ts` validates exact keys, so adding an ad-hoc flag is not a valid model extension. Choice fields constrain values, not per-entry immutability or cross-entry uniqueness.

`src/content/editorial/native.ts` exposes every model field through readFields; validateFields/saveFields use candidate/field-kind validation and expected-store-token CAS. NativeEditorialOptions provides store, publication/submission readers and provenance; no host field policy callback. `src/content/storage/filesystem/transactional-store.ts` editEntry selects the existing qualified entry, changes values only and records history/receipt; broader writes enforce model/creation identity, lifecycle and value validity, not an immutable field-value policy. An entry's record ID is the existing identity; duplicate `course.key` is an ordinary editable value.

Therefore hiding `key` in the inspector or excluding it from AI does not prove immutability. A consumer-only immutable key is not currently established. A wrapper around one editorial call also would not cover native raw entry updates/transactions/history restore. Adding a complete protected-field policy is broader than the needed selected-entry identity projection.

## Options and recommendation

| Option | Benefit | Cost / limitation | Decision |
| --- | --- | --- | --- |
| `course.key` or immutable `legacyQueryIndex` value | Existing scalar Mapping binds it | Duplicate canonical ID or alias metadata; no present native immutability/uniqueness guard; needs policy across all write/restore paths | Do not select as an unguarded consumer-only workaround |
| Fixed per-course pinned presentation with a literal stable prop | Uses supported pin queries and local scalar props; no schema gap | Repeats presentation mappings/literals and risks divergent maintenance; pin order overrides generic Content sort, so does not prove free reorder | Bounded bridge only; not the normalized end state |
| Selected-entry ID as a typed Mapping source | Uses canonical existing record ID, independent of Content order; no duplicate Content field | Small but cross-cutting generic source-kind extension (schema, resolver, authoring/UI, ownership context) | Recommended normal form |
| Synthetic self-reference field with `reference-id` | Existing projection extracts ID | Still duplicates identity, editable self-reference can target another course; no invariant enforcement | Reject as another duplicate-field workaround |

Recommended semantic operation is **read-only selected-entry identity → scalar text prop**. It is not a structured Mapping target or arbitrary expression. Keep full provider/model/entry identity in provenance; a component's `courseId` can be just record ID because its Mapping model/provider are fixed and validated. Never let a model-generated request supply the identity value independently of the selected entry.

## Exact generic implementation surface to inspect/change

Current MappingBinding requires sourceFieldId and every resolver path dereferences it. Merely adding `{kind:"entry-id"}` to MappingSourceProjection while attaching it to an arbitrary field would retain a fake field dependency, causing deleted/empty fields to break identity. Avoid that workaround.

Smallest coherent schema proposal: preserve the existing field-binding shape, and add a strict discriminated entry-identity binding shape with no sourceFieldId (for example a metadata source discriminant). Choose final serialized spelling with the schema owner; do not silently make sourceFieldId optional for every old projection. Both variants must keep target and transform validation, and malformed mixed shapes must fail. Review Mapping schema version/migration policy explicitly; old field bindings must retain meaning without rewriting consumer data. Do not blanket migrate a consumer store to satisfy demo clean-break policy.

Affected concrete sources:

- `src/mapping/model/types.ts`, `validate.ts`, `codec.ts`, `helpers.ts`, `index.ts`: typed source union, strict validation/codec, public type exports and helper defaults.
- `src/mapping/resolver/resolver.ts`: definition resolution currently builds sourceById and blocks missing sourceFieldId; application validates field presence/type before projecting. Branch on metadata source before those field-only checks, resolve the selected entry ID as text, then run normal target/transform compatibility and final assignment. Diagnostics/applied binding provenance must identify entry identity rather than inventing a Content field.
- `src/mapping/resolver/projections.ts` and `compatibility.ts`: current projection definition accepts a required ContentFieldDefinition and `projectContentValue` reads `entry.values[field.id]`. Introduce the entry-source path without broadening structured targets. Treat identity as text; identity transform is sufficient for Pinsel. Existing reference-id semantics must stay unchanged.
- `src/site-project/authoring.ts`: BindingInput currently requires `field`; map creation calls `input.model.fieldId(binding.field)`. Add an explicit typed metadata binding variant with no fake field; preserve existing inference and invalid field detection. Typed pins input is a separate small DSL improvement, not needed to redefine entry identity.
- `src/features/mapping/{controller,presentation,projection-options,source-pane,bindings-pane,bind-menu,editor}.tsx/ts` as applicable: these currently assume binding source is a model field. Display "Entry identity" as a read-only metadata source, show supported scalar targets, support create/rebind and honest diagnostics. Never offer it as an editable Content field.
- `server/public/site-project.mts` exports MappingBinding; `server/public/authoring.mts` exposes DSL. Regenerate supported public facades/types via the repository command; no hand edit to generated mjs/d.mts. Check `type-tests/site-project-exports.json` and `server/__tests__/authoring-dsl.test.ts` against installed APIs. Inspect `server/cli/grammar.ts` and its tests: any generated capability/schema view must describe the actual new source; do not claim a docs-only explanation reaches the Assistant.
- Ownership capability resolution for T5 must mark the metadata source read-only. It must never propose a Content field write or a local prop shadow when selected identity is displayed in preview.

Focused tests: `src/mapping/__tests__/mapping.test.ts` for single/collection projection, absent unrelated field values, duplicate entry IDs across provider/model scopes, text compatibility and invalid target/source mixtures; Mapping storage tests for serialization round-trip; `src/features/mapping/__tests__/editor.test.tsx` for metadata source selection/read-only display; `server/__tests__/authoring-dsl.test.ts` and public export type/installed tests; compiler/collection materialization provenance tests; unchanged structured-target rejection. Add explicit old `reference-id` regression to ensure it still projects a referenced record, not the selected entry.

## Pinsel adoption and historical aliases

Bind canonical selected entry ID into a semantic `courseId` presentation prop in Home pricing and Contact option components. Retain host-owned `COURSE_QUERY_OPTIONS` as the immutable alias mapping: 1→consultation, 2→two-month, 3→four-month; 0/missing/invalid remains undecided. Pricing emits `/contact/?course=<canonical-id>`; Contact accepts that exact canonical ID and resolves incoming numeric aliases to the same stable ID and finds the option by a dedicated identity attribute, independently of DOM order or mutable label. Preserve existing form label/payload behavior; no inquiry delivery change.

Remove `course.order → courseIndex` and selectedIndex coupling only after updating all affected contract/runtime/validation/publication expectations. Keep order for arrangement. Pin Consultation by its qualified existing entry reference; never use order==1. For the other pricing region, explicitly decide membership: fixed existing-course pins are valid but pins define order; alternatively introduce a genuine semantic course role/category field (consultation vs tuition), not a duplicate identity key, and filter on that role while sorting by order. Do not keep order!=1, and do not claim pins preserve arbitrary Content sorting. Membership/role edits need their own allowed behavior and tests; initial scope may remain the existing three records.

Pinsel files: `packages/pinsel-content/src/site/{structure,component-contract,plan-facts,validate}.ts`, `src/models/collections.ts`, `src/invariants.ts`, `src/publication/check-publication.ts`, `src/publication-map.ts`; `packages/pinsel-ui/src/pack.ts`, pricing-card and course-option/contact-form components, `src/scripts/contact-form.ts`; seed migration map and existing migration/structure/invariants/render/script tests. Audit repository references to courseIndex and ?course before finalizing; story fixtures and reference DOM need explicit new-contract handling, while historical seed expectations stay preserved.

Acceptance: reordered Content and reordered Contact DOM options still route old1/2/3 links to the same IDs; label/price changes affect correct shared uses; invalid/unknown IDs refuse or show explicit unsupported state, never retarget another course; both generated links and incoming links tested; exact save/restart/capture/build; no migration of owner's actual D1. Adding/removing courses or minting new legacy aliases is not implicitly part of this first normalization slice.

**Decision recommendation:** after T3, implement the narrow generic selected-entry identity source with installed Pinsel acceptance, rather than duplicating IDs in a mutable key field or expanding native Content protected-field policy solely for this workaround. Keep the immutable numeric alias lookup in Pinsel and write a complete old-prop/new-prop migration map. This is separate from structured lists, singleton changes and any ZFB upgrade.
