## Audit decisions grounded in current schemas

1. **Five semantic singletons** (`site-copy`, `lessons-copy`, `about-copy`, `instructor-profile`, `contact-copy`): retain Content ownership and existing fields. Native Content schema supports `single`, but `src/site-project/model/validation.ts` explicitly requires collection-mode attachments; collection evaluator also requires collection-kind model. Changing only kind breaks current references. Keep one-entry collection as an explicit current capability constraint, with one-entry validation in migration and authoring policy. Do not announce singleton normalization until an upstream single-entry attachment scenario is implemented and installed. Clarify obsolete comments mentioning only old SHA, while retaining the still-current limitation.

2. **Newline fields:** exact source rendering matters. `heroTitleLines` creates spans; `heroLead` strips line breaks; `heroIntro` uses text paragraphs; consultationTopics/consultationFaqTopics create list items; graduatesParagraphs and aboutMessage create paragraphs; testimonial.quote splits on literal newline. `contract-components.tsx` lines() filters blank lines, while voice detail uses a different split. Do not globally split every long-text field or normalize whitespace. Current Mapping resolver rejects list/object target fields (`structured-target-unsupported`, existing regression test), despite Content supporting structured fields. Retain bytes and text semantics initially. A justified later enhancement could add semantic list-item child components plus mapped child Content records, but it requires per-field reversible migration, stable child IDs and exact blank-line behavior; no unsupported arbitrary array Mapping assumption.

3. **Manual pins:** current public `CollectionModeInput` (server/authoring.d.mts and src/site-project/authoring.ts) STILL lacks pins, although Mapping schema has pins. Existing post-DSL patch is therefore not obsolete. Minimal justified generic change: add validated `pins` to public collection input, use existing qualified Entry refs, generate exact current query semantics, and prove deleted pin does not select a fallback. Preserve the deliberately impossible condition because pins are additive to query results; simply removing that condition can silently select another entry. Migrate only initialization authoring code, not saved native records, when serialized output is identical.

4. **Templates / excessive fragments:** 177 compositions are 14 actual pages + 163 mapped internal fragments. This count is not 177 pages. Nested Global templates remain explicitly refused (`src/composer/reuse/__tests__/reuse.test.ts` nested-template). Repeated frame header/footer already share Content and Mapping sources; do not replace them with unsupported nested Globals. A single shared source is a live reference, not a detached pattern. Parent placement reorder can remain local while source text stays shared. Recommend name/role classification and grouped tree presentation before destructive fragment consolidation. Remove only fragment boundaries proven redundant by equal owner/entry/slot context; require HTML, identity and shared-use comparison. Per-year/FAQ-group sections and per-Note sources still encode parent-dependent filters and multiple Content models; no current evidence allows collapsing them generically.

5. **Distinct excerpts:** preserve home-result vs result-entry/result-year, home-voice vs testimonial, home-faq vs faq-item, target-item home vs lessons, instructor-profile.homeBio vs lessonsBio/aboutMessage, separate timeline groups, knowledge-card.title/description vs referenced Note. result-year.declaredCount remains editorial and is not recalculated from 105 detail records. Note IDs equal slugs historically; reference-id links currently rely on this and slug changes must not silently break Knowledge cards.

## Minimal course identity normalization proposal

Existing record IDs are `consultation`, `two-month`, `four-month`; existing aliases are `?course=1/2/3` respectively, and 0 means undecided. Today course.order drives Home link courseIndex, Contact option position, Lessons consultation equality1 and pricing inequality1. A reorder can therefore change course identity in four separate places.

The [course identity decision](composer-course-identity-decision.md) recommends a narrow generic **selected-entry ID Mapping source**, not a duplicate `course.key` field. Native Content currently has no protected arbitrary-field policy: a duplicate key would remain editable, and hiding it in one inspector would not enforce immutability across saves, transactions and history restore. This generic source capability is **not implemented**; implement and verify it in Composer before adopting its exact installed revision in Pinsel. Preserve existing field-binding semantics and strict source validation. Identity must come from the selected qualified entry, without an invented field dependency or a writable Content target.

Keep all eight existing course fields and every old value, including `order`, whose meaning becomes arrangement only. Bind the existing canonical entry ID into a semantic `courseId` prop in Home pricing and Contact options. Preserve the historical numeric URLs: Pinsel's fixed alias table maps 1→consultation, 2→two-month, 3→four-month. Pricing resolves the stable ID to its existing numeric URL; Contact resolves the incoming alias to that stable ID and locates the option by a dedicated identity attribute, independently of DOM order and mutable labels. Keep option label/value behavior intact and leave missing/invalid/0 input undecided. Do not implicitly add courses or allocate new aliases.

Consultation membership must use its qualified existing entry reference, never `order == 1`. The other pricing region must also express membership independently of order: fixed existing-course pins are supported but determine their own order; alternatively, a genuine semantic role/category field can select tuition records and allow sorting by `order`. Decide and test that membership policy explicitly. Do not keep `order != 1` or claim pinned membership preserves arbitrary Content sorting. A role field describes content; it is not a substitute duplicate identity field.

Migration tooling should accept a fresh public snapshot and produce a candidate SiteProject + audit map, initialize into a NEW configured staging root through public initializeAuthoringWorkspace, and capture/build there. Never modify .native-authoring files directly, rebuild from Git seeds over native edits, or claim four-domain atomicity. Each entry receipt includes old/new field IDs and canonical value hashes; preserve historical original snapshots. Require the expected model shape and qualified existing entry IDs; reject unknown identities and ambiguous numeric alias mappings. Include a complete old-prop/new-prop map for `courseIndex` to `courseId`, and remove positional selection only after all runtime, contract and validation uses have been updated. Idempotence is candidate-transform equality, not silently reimporting into existing stores. Actual authority switching remains held.

Focused tests: reordered courses still show intended Consultation and class prices; all legacy aliases retain original course with reordered options and edited labels; generated numeric links and incoming numeric aliases resolve through the same stable IDs; negative/fractional/overflow aliases leave undecided and unknown selected identities never retarget another course; shared price changes Home+Lessons and labels Contact; existing excerpts unchanged; deleting referenced consultation refuses or visibly reports missing target (never selects another course). Dedicated historical baseline migration test retains original numeric markup/14-route proof; new-contract tests validate identity independent of order. Update component versions and preserve old captured-render compatibility explicitly instead of weakening seed fixtures.

## Supported operation boundaries

Human native Content field editing uses the Content editorial owner; the host inspector points bound values to that source. Host structural edit supports validated local fields, local reorder/remove and parent placement reorder, with captured owner/revision and durable receipts. It explicitly refuses editing a shared Mapping source through a local Composition target. These operations cannot perform an atomic four-domain schema migration. Public initializeAuthoringWorkspace into a new root + public coherent capture/compile are the supported staged migration primitives. Existing Composition commands support insert/copy, but do not infer that every host-document UI offers those commands yet. Shared-source structure edits must be explicitly reviewed as shared impacts.

Sitemap pure commands support addRoot, addChild, addSibling, updateProps (title/slug/source/notes), remove, duplicate, move/reorder; one root only, no cycles, source initially unassigned. Assignment can reference an existing Composition or Mapping; adding a tree row does not create a complete routable Composition. Duplicate copies source refs, so it may remain a live shared source rather than a detached page copy. Current schema has navigation lists separately from tree. Existing Pinsel nav-link Content mappings still drive visible chrome: adding a Sitemap child alone is not proof a header/footer link appears.
