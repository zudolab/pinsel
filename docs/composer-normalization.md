# Normalization decisions for native authoring

The initial audit used independently installed Composer
`533be688e51ff150bce5e9bc87d2b07e62ebaec3` and Pinsel pack0.3.0 on2026-11-16.
Its grammar exposed read-only entry identity and no published Global templates.
Package source paths and line numbers below retain that historical evidence; they
are not a fresh audit of every later package or permission for consumer code to
import private implementation. Updated dispositions identify work implemented
since that audit. The [compatibility ledger](composer-compatibility.md) is the
source of current installed pins and scenario outcomes; the native Note contract
is now pack0.4.0/native-v3, not the old fixed-route topology.

Same-owner small fragments may be consolidated only where installed editing demonstrates a usability defect and full reference/selection equivalence is rehearsed. Do not hide page inventory errors by deleting internal compositions. |

## Preservation and remaining authoring work

All 181 baseline Content fields and 128 qualified Content references retain their
owner and field identity. The [field inventory](composer-migration-inventory.md)
and [reference map](composer-migration-reference-map.json) remain historical
baseline evidence; the [staged migration recipe](composer-course-migration.md)
and [compatibility ledger](composer-compatibility.md) record actual transformations
and verification. Preserve all original seed, assets and history.

Home excerpts, instructor biographies and course descriptions remain distinct from
detailed records. Knowledge-card copy remains independent of Note copy. Result
counts remain authored values rather than inferred totals.

[T6](https://github.com/zudolab/pinsel/issues/55) owns these installed scenarios.
Since this audit, dynamic Note/Course creation and publication and supported
component removal have passed at the exact pins in the compatibility ledger.
The current [static route](native-route-acceptance.md),
[family creation](composer-family-acceptance.md),
[family follow-up](native-family-followup-acceptance.md) and
[canonical shared-source](canonical-shared-sources.md) recipes describe implemented
operations and their required evidence. The ledger distinguishes completed phases,
partial outcomes, separate recoveries and remaining acceptance; the initial audit
is not a current blanket claim that those operations are missing or all passed.
A supported schema or source recipe alone does not establish an installed user
scenario pass. Source regeneration may never overwrite native authoring to
simulate support.
